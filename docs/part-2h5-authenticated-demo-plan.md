# BUSHO — Part 2H.5 authenticated demonstration plan

**Prepared:** 2026-11-08  
**Branch:** `feature/chhattisgarh-operational-workflow`  
**Status:** Engineering plan; no non-production environment or identities provisioned.

## Objective

Prove the worker → supervisor → storekeeper workflow with separate authenticated identities and two synthetic facilities, without writing to the connected operational Supabase project or changing production.

This milestone is not complete when a page returns HTTP 200. It is complete only when browser sessions, database authorization, persistence, audit history and negative permission tests all agree.

## Current environment facts

- The connected Supabase project is healthy, but has zero Auth users, profiles, facilities, workers, facility assignments, scope assignments, reports, audit logs, inventory items, inventory snapshots and replenishment requests.
- All 23 public tables currently have RLS enabled.
- The live project has only the two original migrations applied. The feature-branch operational migrations are not live.
- Supabase currently has no development branches. Creating one can incur additional compute charges and requires owner cost approval.
- The provisioning and facility-registry Edge Functions are present in the feature branch but are not deployed to the connected project.
- The latest Vercel preview is READY for commit `a9a04a77710b03afaa0b93ffca91c71760498f3b`. Portal route and asset smoke checks returned HTTP 200. This is not authenticated browser validation.
- PR #5 remains draft and production remains on `main`.

## Environment decision gate

Before provisioning any identities, the project owner must choose one of:

1. **Supabase Branching** — create a dedicated development branch from the connected project. Confirm the displayed cost and approve it before creation. Confirm that the branch contains the expected migration baseline and has independent Auth, database and Edge Function configuration.
2. **Separate non-production Supabase project** — provision an explicitly named test project with independent secrets, Auth settings, URL allowlist and database. This avoids placing synthetic test data in the operational project.
3. **Local Supabase stack** — use local Supabase CLI services and local Auth/Storage/DB with synthetic fixtures. This is preferred when available and practical, but does not prove hosted Auth/Edge Function configuration.

Do not create a branch, project, Auth user, facility, assignment, migration or Edge Function deployment in the connected operational project as a shortcut.

## Synthetic fixture specification

Use only synthetic names and identifiers, visibly marked `SYNTHETIC — TEST ONLY`.

| Fixture | Purpose |
|---|---|
| Facility A | Synthetic SHC-AAM-like test facility in a clearly fictional test namespace |
| Facility B | Second synthetic facility used to prove cross-facility isolation |
| Worker A | Assigned only to Facility A |
| Worker B | Assigned only to Facility B |
| Supervisor A | Scoped only to Facility A |
| Supervisor B | Scoped only to Facility B |
| Storekeeper A | Assigned only to Facility A |
| Storekeeper B | Assigned only to Facility B |
| Administrator | Provisioning authority limited to the isolated test environment |

Use non-routable/test email addresses and random test-only passwords generated by the environment. Never use real worker identities, patient details, phone numbers, Aadhaar/ABHA identifiers or clinical narratives.

Every synthetic facility, report, inventory item, replenishment request, external DPDMIS reference and audit event must carry a test classification. Synthetic references must be unmistakable and must never resemble valid production transaction IDs.

## Acceptance matrix

### Authentication and role gates

- Worker A can sign in to the worker portal.
- Supervisor A can sign in to the supervisor portal.
- Storekeeper A can sign in to the storekeeper portal.
- Wrong-role access is denied even when the Auth session is valid.
- Pending, suspended and profile-missing accounts are denied.
- Logout clears the local session and subsequent protected REST requests fail.
- Session restoration revalidates the server-controlled profile.

### Worker reporting

- Worker A can load only the server-assigned Facility A context.
- A report draft uses the worker ID and facility ID resolved from the authenticated server-side assignment, not browser-supplied IDs.
- Structured items preserve source phrase and review-required metadata.
- Submission is acknowledged only after the server confirms the submitted state.
- Repeating a submission after an ambiguous network result does not create a duplicate report.
- Worker A can see their own report history and correction request.
- Worker A cannot read or mutate Worker B's report or change facility assignment.

### Supervisor review

- Supervisor A sees only records allowed by Facility A RLS scope.
- Supervisor A can verify, request correction with a reason, reject or escalate according to allowed state transitions.
- Original worker text and all report events remain auditable.
- Supervisor A cannot access Facility B records or perform storekeeper-only fulfilment.
- Report verification does not itself create a replenishment order or mark stock as received.

### Storekeeper fulfilment

- Storekeeper A sees only Facility A replenishment requests.
- Allocation requires an external allocation reference.
- Dispatch requires an external challan/dispatch reference.
- Receipt requires a goods-receipt reference and a valid cumulative quantity.
- Partial receipt followed by final receipt produces correct immutable movement deltas.
- Exact retry of the latest receipt is idempotent.
- Replaying an older partial receipt after a later receipt is rejected.
- Storekeeper A cannot approve a supervisor recommendation or alter/delete posted inventory movements.
- No purchase order or DPDMIS transaction is claimed to exist unless the external system independently supplies its reference.

### Cross-facility negative tests

For every relevant table and RPC, test direct REST/RPC attempts—not only UI hiding:

- Worker A reads Worker B report: denied or zero rows.
- Supervisor A reads Facility B report: denied or zero rows.
- Storekeeper A reads Facility B replenishment: denied or zero rows.
- Worker attempts supervisor review RPC: denied.
- Supervisor attempts storekeeper allocation/dispatch/receipt RPC: denied.
- Storekeeper attempts supervisor approval: denied.
- Browser roles attempt direct insert/update/delete of inventory movements: denied.
- Unauthenticated requests attempt all protected operations: denied.

Record the expected SQLSTATE/HTTP outcome and actual result. A UI-only denial does not pass an RLS test.

## Evidence bundle

For each run, retain:

- Test environment/project reference (never secrets).
- Exact migration versions applied and migration order.
- Fixture manifest with synthetic labels.
- Browser version and test timestamp.
- Commit SHA and Vercel deployment ID/SHA.
- Per-role sign-in and workflow screenshots or traces with tokens and personal data excluded.
- REST/RPC request outcomes with authorization headers redacted.
- Database assertions for row counts, scope and immutable movement totals.
- CI run URL and test output.
- Cleanup/reset confirmation for synthetic data.

## Exit criteria

Part 2H.5 can be marked complete only when:

1. A non-production environment is explicitly approved and isolated.
2. The feature-branch migrations apply cleanly there in CI-equivalent order.
3. Required Edge Functions are reviewed, configured and deployed only to that environment.
4. Synthetic users/facilities/assignments are provisioned through the intended administrative path.
5. All positive and negative acceptance tests pass in real browser sessions.
6. Two-facility isolation is demonstrated at the database layer.
7. Evidence is attached to the milestone and progress tracker.
8. Cleanup/reset is demonstrated without touching operational production data.

## Explicit non-goals

- No production migration or release.
- No real facility roster import.
- No real medicine catalogue approval or SKU normalization.
- No real DPDMIS/CGMSC transaction or API integration.
- No stock-balance claim before an approved stock accounting SOP and complete movement coverage.
- No real patient or workforce data in the test environment.
